General arrangement

Sheet 1 of 7 · units: pixels

JSX for
microcontrollers …Raspberry Pi, desktop, terminal and the browser. One portable core. Several backends.

mjsx is one file of ES5-safe JavaScript — 2,514 lines — that lays out, draws and handles touch for a whole interface, and it does the drawing through ten native calls. Anything that can fill a rectangle and report the time is a target: a 1.28-inch round panel wired to a chip, an ANSI terminal, a browser tab, a native window, a PNG on disk.

No virtual DOM, no reconciler, no dependencies. A dirty frame simply redraws itself.

02

General notes

Sheet 2 of 7 · read before use

No VDOM, no reconciler N1

State goes in through UI.set; the frame is marked dirty; the next frame is drawn from scratch. There is no retained tree to diff and nothing to keep in sync — the screen is a pure function of the state, recomputed.

Width-in, height-out N2

measure() takes an available width and returns a height; draw() places at a point. Deliberately not two-dimensional constraint solving — see N6.

The touch machine lives in the core N3

A 6-pixel drag slop, scrolling, flings with per-zone velocity, long-press repeat. A backend feeds raw UI.pointer(id, phase, x, y) and inherits identical feel — a fling on the panel and a fling in a browser tab are the same code.

ES5 / MicroQuickJS subset, on purpose N4

var, no arrows, no let. The same file runs unmodified inside a chip's embedded interpreter and in a browser's own engine. No branch on the host, no build for the device.

The JSX transpiler is 312 lines, in-tree N5

It rewrites JSX elements into h() calls and leaves every other byte alone — app code is already in the subset, so there is nothing to down-level. It is written in the same subset it compiles, so it runs in a browser, or inside the chip interpreter itself.

Real flexbox was deliberately not built N6

Yoga is a genuinely different algorithm, it has no answer for scrolling here, and its C++20 requirement is an unverified toolchain risk on the Xtensa compiler. If it ever lands it is a sibling layout phase behind the same Element → Frame contract, not a fork.

03

Detail A — the ten-call contract

Sheet 3 of 7 · section A—A

Everything above the section line is one file and never changes. Everything below it is a backend: ten functions and a loop. That line is the entire porting contract — there is no second interface, no capability negotiation, no per-target branch in the core.

  1. 4

    Nothing above the line changes per target

    Layout, hit-testing, gestures, keyboards and modals are one file. Porting to new hardware does not mean forking any of it.

  2. 5

    Ten functions, plus a clock

    The ESP32 stdlib table declares exactly these — no poly, no blit required. A few extras are probed for with typeof and simply not used when absent.

  3. 6

    A new backend is ten functions and a loop

    Own the loop: call UI.ticker(), and when it or UI.dirty() says so, call UI.render() and present the surface. Feed input back through UI.pointer and UI.key.

Schedule A — required native calls
No.CallWhat the backend must do
A1gfx.clear(color)Fill the whole surface. Start of every frame.
A2gfx.rect(x, y, w, h, color, radius)One-pixel outline, optionally rounded. Radius may be 0.
A3gfx.frect(x, y, w, h, color, radius)Filled rectangle, optionally rounded. The workhorse call — most of a frame is this.
A4gfx.circle(x, y, r, color, filled)Centre, radius, and a boolean fill.
A5gfx.line(x0, y0, x1, y1, color)One pixel wide. Thick lines are drawn by the core as parallel one-pixel lines.
A6gfx.text(x, y, size, color, str)Draw a string at an integer size multiplier, top-left origin. The core never rasterizes a glyph — font choice is entirely the backend's.
A7gfx.clip(x, y, w, h)Set the clip rectangle. A single rect, not a stack: the core intersects nested clips itself and always hands over one honest rectangle.
A8gfx.unclip()Remove the clip rectangle.
A9gfx.width()Logical surface width, in pixels.
A10gfx.height()Logical surface height, in pixels.
A11sys.millis()Monotonic clock in milliseconds. Drives timers, cursor blink, long-press and fling velocity.

Optional and probed for, never required: a persistent sys.store / sys.fetch pair, gfx.poly for device-resolution path fills, gfx.blit for external pixels such as a camera frame, and a font-metric override for backends whose "pixels" are not pixels.

Detail C — round glass

Sheet 6 of 7 · Ø 240 · plate 4

A circle is not a rectangle with rounded corners. On round glass a row does not get the display's width — it gets the chord of the circle at its own height, and the row nearest the rim gets far less than the row through the middle. Layout, the keyboard and the footer controls all take that as an input rather than pretending it away.

  1. 7

    OK is parked in the bottom arc

    The sliver below the last key row is space the grid can never use — a full-width row down there would be mostly bezel. Putting the confirm key in it costs the keyboard no height at all. Without the insets, SPACE and OK sit half under the rim.

  2. 8

    One call, any boundary

    Each item sits where the ray from centre at its angle meets the boundary, pulled inward by the item's own size. On round glass that boundary is the rim; on square glass it is the rectangle's perimeter, so a bottom arc becomes the bottom edge and a wide one spills around the corners onto the sides. Items stay upright — only their positions follow the edge.

Schedule C — keyboard layout, chosen by fit

  1. kbW = gfx.width()◂square glass The width the keys actually get.
  2. kbW = chord × 2◂round glass Measured down where the bottom rows sit, not across the middle: "a 240px circle measures 240 across the middle and only ~178 there."
  3. kbW ≥ 220→QWERTY Ten columns want about 22 px each.
  4. kbW ≥ 115→T9 Four columns want about 28 px each.
  5. otherwise→STRIP One scrolling row — below T9's width, only a single row is honestly tappable.
  6. key height < 30→full screen If the docked keys come out under a finger's height, docking is a fiction: the keyboard takes the whole display instead. Nobody should have to opt in to legible keys.
  7. layout = "numbers"→number pad Named, not auto-chosen. A stated preference is a decision, not a suggestion — a named layout is honoured exactly, however cramped.

Text entry, on the device itself N7

Four keyboard layouts ship in the core: QWERTY, T9, a number pad and a scrolling strip for tiny screens. Nothing about them is per-board — they measure the room the keys actually get and pick.

The host declares the glass N8

Round is a fact the host states, not one the framework guesses: firmware seeds a stored key, UI.isRound() reads it once and caches the answer. Web and simulator leave it unset, so the answer is square unless something says otherwise.

Hardware, from JavaScript N9

sys.gpio(pin, op, value) reads, writes or samples the ADC; sys.i2c(addr, reg, value) moves one byte on the board's shared bus. The firmware refuses, with −1, any pin the active board's display or touch controller uses — the denylist is built from the same defines that wire those peripherals. A motion module reports acceleration, rotation and temperature into state.

Distribution notice

This is a hobby project, open-sourced as-is, and it is not published: there is no package on npm — being private is deliberate — and the repository is not on GitHub. There is nothing to install from a registry today. Pin to the repository if you use it. It is MIT licensed, it drives four boards daily, and its known limitations are written down in the repo rather than hidden: fixed-pixel examples do not fit every canvas size, font metrics are a documented backend override point that some runners forget to wire, and real flexbox was deliberately not built.
