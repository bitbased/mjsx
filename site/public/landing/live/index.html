Play it. That is the pitch.

That panel is 2,527 lines of ES5 running a sixty-step-a-second game loop and painting it through ten drawing calls. The same file runs on a $6 microcontroller. Nothing here is a video, a canvas demo, or a re-implementation — /mjsx-sim.js is the engine itself. Hold and drag to fly; arrows and space also work.

240 × 240 · round · GC9A01
hold & drag to fly · tap to fire

There is no virtual DOM and no reconciler. A frame that is dirty redraws its whole tree — no diff, no keys, no fibers. That is why the engine is one file you can read in an afternoon instead of a framework, and it is what the counters beside this panel are counting: a hundred draw calls, laid out and painted, every frame, in under five milliseconds.

The app is plain JSX with no build step. Your browser transpiled it on load with packages/core/src/jsx.js — 312 lines, the same transpiler that runs when a bundle is pushed to a board. There is no bundler in this page and none on the chip.

draw calls · frame — layout+paint — fps — camera —

Written in the ES5 subset MicroQuickJS accepts: no classes, no arrow functions, no template literals. Not nostalgia — that is what the engine on the chip parses, and a linter fails the build if a file drifts out of it.

touch is a real event

Draw on it.

One input model, every host. Your mouse became UI.pointer(id, phase, x, y) — the identical call an ESP32 touch controller makes, an SDL window makes, and a browser mirror forwards over a websocket. The engine has one touch state machine: taps, drags, long-presses, momentum flings and scroll all come out of that one entry point.

Hit boxes are registered as the frame paints, so the drawn rectangle and the touchable rectangle are the same rectangle by construction. They cannot drift apart, because there is only one of them.

text entry, on a chip

Type on it.

172 × 320 · 1.47″ JD9853
tap a field, then use the keys

The engine owns the editing state, so your render stays a pure description. Text, caret and scroll live against the field's id; typing never dirties app state and never rebuilds the form. That is what lets a keystroke become a pixel without a round trip through your data.

It is also why the full-display keyboard needs no synchronising code. The field it shows is not a copy — state is keyed by id, so a second node with the same id is the same field. Two views, one piece of state, zero lines to keep them in step.

Ten calls, and a clock.

This is the entire hardware contract. clear, rect, frect, circle, line, text, clip, unclip, width, height, and sys.millis(). Implement those eleven functions and every app in this repository runs on your hardware. Below is the real op stream from the panel above, as the engine emitted it.

one source, five panels, at once

  
No breakpoints. No second code path.

  

    Layout is width-in, height-out: a node is told its width and reports
    its height. Nothing ever reports a width. That single rule is why the same
    tree fits a 172-pixel column and a 480-pixel window with no media query, no
    breakpoint and no second code path — and why porting to a new panel is
    telling the engine a number, not rewriting a layout.
