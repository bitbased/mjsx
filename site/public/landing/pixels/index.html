JSX for microcontrollers. And for the Pi, the desktop, the terminal, and the browser.

One portable core describes the screen. Underneath it sits a line so narrow you can count it: ten drawing functions and a clock. Everything above that line is the same JavaScript file, whether it is running inside a chip's embedded interpreter or inside a browser tab.

No virtual DOM. No reconciler. State changes, the frame is dirty, the frame is drawn again — pixel for pixel.

01 — How it works

The whole porting contract fits on one screen.

mjsx-core draws through two globals a backend supplies before the core loads: gfx and sys. It assumes ten gfx calls and one sys call exist, and nothing else. A backend is whatever realises those ten.

All ten calls200 × 1401×

Pick a call on the left and the picture answers. Every shape here — and every screen on this page — was drawn by a Canvas2D object in this file that implements exactly those ten functions, plus a hand-typed 5×7 bitmap font at mjsx's own default metric (advance 6, line height 8). Writing a backend really is that small.

Hit-testing can't drift

A control registers its hit rect at the exact rectangle it was drawn at, so what you tap and what you see are the same number.

The touch state machine is in the core

Drag slop, scrolling, fling, long-press and auto-repeat live above the ten calls, so every backend gets identical behaviour from identical code.

The transpiler is written in the language it compiles

~300 lines of the same ES5 subset it emits, with no dependencies and no host APIs — so it can run in the CLI, in a browser, or inside the chip's own interpreter.

02 — The app

This is the whole counter, and it is the whole idea.

Ambient globals, no imports, no build step for the app author. Tap the button, the state changes, the screen is drawn again to match. That is the render model, stated in nine lines.

examples/counter/app.jsx 
function App() {
  var count = UI.state.count || 0;
  return (
    <box pad={em(2)} gap={em(2)}>
      <text text={'COUNT: ' + count} size={3}
            color={UI.theme.text} align="center" />
      <Button label="+1" size={2}
              onTap={function () { UI.set({ count: count + 1 }); }} />
    </box>
  );
}

UI.mount(App);

em() is text-relative, not pixel-relative

em(2) is two line-heights of the current font, resolved at call time. Swap the backend's font scale — a terminal cell instead of a panel pixel — and the padding follows the text instead of staying panel-sized.

Button is not privileged

It is nineteen lines built from box and text, the same primitives your app uses. None of the ready-made components are mandatory; any of them can be rebuilt in app code when they don't fit.

ES5 on purpose

The core is written in the MicroQuickJS-safe subset deliberately. The same file runs unmodified on a chip's embedded interpreter and in a browser's own engine — no branching on the host, no second build.

No reconciler, and that is the feature

There is no retained tree to diff and no VDOM to allocate. State goes in through UI.set, the frame is marked dirty, and the frame is drawn again.

03 — Where it runs

Six backends. The same ten functions, six times.

Nothing above the porting line is special-cased per target. On the chip gfx.frect is a C function writing to a panel; in the headless renderer it writes into an RGBA buffer; in a terminal it writes into a sub-pixel buffer that is flushed as ANSI escape codes.

pure-js

Headless rasteriser into an RGBA buffer; writes PPM and PNG. The reference implementation, and the renderer the browser and window backends draw with.

backends/pure-js

terminal

Near-square pixels in a terminal: two sub-pixels per character cell via the half-block glyph. A real raw-mode CLI app, and the example picker.

backends/terminal

SDL window

Device simulator in a native window: square, rounded-corner and round-display masks, size presets for the real panels, and a sub-pixel HD mode.

backends/sdl

Browser mirror

The UI in a browser tab over a socket — pixels out, real input back, including genuine per-finger multitouch. A device mirrors its own screen the same way, to a /remote page.

the browser backend, under backends/

WASM

The same MicroQuickJS engine source a chip runs, compiled through Emscripten. Engine parity for testing — not a reimplementation that drifts.

backends/wasm

ESP32

The real thing: a minimal reference firmware showing where a panel driver plugs in, and a pusher that bundles core plus examples to a live board over TCP — no reflash. Firmware updates itself over WiFi.

backends/esp32

04 — Round glass

A circle is not a rectangle with the corners hidden.

On the 1.28 inch round panel, layout fits the chord of the circle at each row's own height. So the keyboard becomes a trapezoid, and no key ends up under the bezel.

1.28 in round240 × 2401×

rim, row bands, and the width each row actually gets

The width that decides is the width the keys get

A 240 px circle measures 240 across the middle and only about 178 down where the bottom rows sit. Ten QWERTY columns need 220, so the layout picks itself: this glass gets T9, not a QWERTY squeezed under the rim.

Rows inset to their own chord

Each key row is inset to the chord at its height, so the grid narrows going down and the outermost keys stay on the glass. Toggle the overlay to see the four bands the four rows are cut from.

OK moves into the arc

In exclusive mode the mirrored input is pushed a tenth of the display down, off the narrow top arc; the keys stop short of the bottom arc; and OK moves into that arc — space the grid could never use, so it costs the keyboard no height.

ArcFooter: controls on the rim

Each item sits where the ray from screen-centre at its angle meets the boundary, pulled inward by its own size. On round glass that boundary is the rim; on square glass it is the perimeter, so a bottom arc simply becomes the bottom edge. The same call serves every shape.

Four layouts, and they choose themselves

QWERTY

Where ten columns of about 22 px fit — roughly 220 px and up. Symbol pages so every glyph the face carries is typeable.

T9

Where four columns of about 28 px fit. Letters-first faces, multi-tap cycling, hold a key for its digit.

Number pad

Digits, with OK on the utility row rather than spending a whole row of height on it.

Strip

A single scrolling row of characters for glass with no room for a grid at all. Drag to scroll, tap to type.

Ask for a layout by name and you get it exactly, however cramped — a stated preference is a decision, not a suggestion. Ask for auto and it measures the room the keys will actually get. And when docked keys would come out under 30 px, docking is a fiction: the keyboard takes the whole display, with a live mirror of the focused field above it.

05 — Hardware

Pins and buses, from JavaScript.

The same script that lays out a screen can read a pin. Two natives on the bridge firmware give direct hardware access, and a motion module pushes readings in as ordinary state.

sys.gpio(pin, op, value)

Read with pull-up, drive high or low, or take an ADC count. Returns -1 for a refused pin — the firmware fences off every pin the active board's display and touch controller use, from the same defines that wire them.

sys.i2c(addr, reg, value)

One byte of a device on the board's shared bus: omit the value to read, pass 0–255 to write. It is the same sequence as the bridge's bring-up tool, so a bus scan is a UI rather than a serial session.

Motion

Accelerometer, gyroscope and temperature. The module pushes state patches on its own schedule and only when a reading actually moved, so a view never polls — it just renders state and is redrawn when the state changes.

Everything here is checked before it is called, the way the examples do it — other backends do not have these natives, and an app that runs on a desktop and a chip has to know which one it woke up on.

Honest status.

mjsx is a hobby project, open-sourced as-is. It is not published to npm and it is not on a public git host yet — so there is no install line to copy here, and any that appears elsewhere is not this. If you use it, pin to the repository.

It was ported out of a working ESP32 firmware's UI engine and generalised until nothing in it assumed a board, an engine, or a particular way of turning a draw call into pixels. It drives a four-board fleet daily, which is the only benchmark being claimed on this page.
