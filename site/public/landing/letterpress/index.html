Specimen No. 1  —  mjsx, a JSX engine for small glass /

mjsx.

JSX for microcontrollers, Raspberry Pi, the desktop and the browser — one portable core, several backends, ten native calls between them.

The engine is one file. packages/core/src/mjsx.js holds all of it in 2,526 lines: h(), the layout pass, hit‑testing, and the touch state machine. There is no virtual DOM in it and no reconciler — a frame that is dirty is redrawn from the top, and the rectangle you can tap is registered at the exact rectangle that was drawn, so the two cannot drift apart.

Below that file there is a line, and below the line there are exactly ten drawing calls. Everything that has ever been ported is those ten.

Written in an ES5 subset on purpose — the same characters run on a chip’s embedded interpreter and in a browser, with nothing transpiled between them.

§ I  —  the porting contract

Ten calls, and a clock.

Marginal A handful of calls are optional and probed with typeof before use: gfx.poly for real polygon fills, gfx.blit for external pixels, sys.store / sys.fetch for persistent settings. The core works without all of them — absent blit, a canvas element draws a crossed placeholder frame and says so.

A backend is not a plugin, a driver, or an adapter class to subclass. It is whatever supplies ten functions on a global named gfx and one on a global named sys. That is the entire native surface the core assumes exists, and nothing above the line is special-cased per target: the same layout pass that measures a column for a 3.5‑inch panel measures it for a terminal window, and the whole difference between them is which function fills a rectangle.1

The ten calls, and what a backend must do with each
CallWhat the backend must do
gfx.clear(color)Fill the whole surface. The start of every frame.
gfx.rect(x, y, w, h, color, radius)One‑pixel outline, optionally rounded. radius may be 0.
gfx.frect(x, y, w, h, color, radius)Filled rectangle, optionally rounded. The workhorse.
gfx.circle(x, y, r, color, filled)Centre, radius, and a boolean fill.
gfx.line(x0, y0, x1, y1, color)One pixel. Thick lines the core draws itself, as parallel ones.
gfx.text(x, y, size, color, str)Draw a string at an integer size, top‑left origin. Font choice is entirely the backend’s.
gfx.clip(x, y, w, h)Set the clip rectangle — one rect, not a stack. The core intersects nested clips itself and hands down one honest rectangle.
gfx.unclip()Remove it.
gfx.width()Logical surface width, in pixels.
gfx.height()Logical surface height.
sys.millis()A monotonic clock in milliseconds. It drives timers, the caret blink, long‑press and fling velocity — and it is the eleventh thing, which is why the contract is never described as ten alone.

On the chip the same names bind to C functions; in the headless renderer they bind to plain JavaScript that writes into an RGBA buffer; in the terminal they bind to something that writes sub‑pixels flushed as escape codes. A stream backend is the same idea pointed at a wire: each call appends a compact operation instead of touching a local surface, and the receiving end is just another backend replaying those ten calls against a surface of its own.

§ II  —  a frame, and what made it

No tree is kept. The frame is simply drawn again.

State goes in through UI.set(patch), which shallow‑merges and marks the frame dirty. The next frame is built and drawn from scratch: measure, then draw, width in and height out. Nothing is diffed, because nothing was retained to diff against. Hit rectangles are registered during that same pass, at the coordinates the control was actually drawn at.

§ III  —  where it runs

Six ways to answer the same ten questions.

Marginal The engine was ported out of a working ESP32 firmware’s UI code and then generalised until nothing in it assumed a board, an interpreter, or a particular way of turning a draw call into pixels. The device is not the port. The device is where it started.
Pure JS
A headless rasteriser into an RGBA buffer that writes real image files. The reference implementation, and the renderer the browser mirror and the desktop window both draw with.
Terminal
Near‑square pixels in a terminal: two sub‑pixels to a character cell by way of the half‑block glyph. Text is the terminal’s own font, so the font metrics are overridden after the core loads. There is a one‑shot renderer, a real raw‑mode interactive app, and an example picker.
Desktop window
A device simulator in a native window: square, rounded‑corner and round masks, size presets for the real panels, a high‑definition sub‑pixel mode, and host‑font text. Its optional library is the only native dependency anywhere in the tree.
Browser mirror
The interface in a browser tab over a socket — pixels out, real input back, including genuine per‑finger multitouch. On the device side an operation recorder mirrors the screen the same way, by replaying a frame’s call list into a page.
WASM
The same MicroQuickJS engine, compiled. Not a reimplementation and not a lookalike: the identical bytecode a chip executes, run for engine parity in testing.
ESP32
The real thing, in two halves. A minimal reference firmware — MicroQuickJS plus the ten‑call glue — showing exactly where a panel driver plugs in; and the half that runs daily, which bundles the core, a small device shim and every example into plain JavaScript and pushes them to a board over TCP with no reflash at all. That firmware updates itself over WiFi.
§ IV  —  round glass

A circle is not a rectangle with the corners painted out.

Marginal Scrolling changes too. On round glass every scroll zone is unconditionally given a quarter‑screen of extra range at the end, so the last rows can be lifted out of the narrow bottom arc and read in the wide middle.

Fit a layout to the bounding box of a round display and the outermost keys of the bottom row disappear under the bezel. So the layout fits the chord instead — the width the glass actually offers at each row’s own height. A 240‑pixel circle measures 240 across the middle and, in the band a keyboard’s bottom rows occupy, only 154 — and that is the number the layout is given.

A keyboard therefore comes out a trapezoid, each row inset to its own chord, and no key hides. In exclusive mode the mirrored field is pushed a tenth of the display down, off the narrow top arc; the keys stop short of the bottom arc; and the OK key moves into that arc — space the grid could never have used, so it costs the keyboard no height at all. Controls that want the edge go on the rim.

§ V  —  further particulars

Set in small type, as such things are.

  1. 01Text entry, on glass that has no room for it. Four layouts — QWERTY, T9, a number pad, and a single scrolling strip for the smallest displays. Left to itself the keyboard chooses by the width the keys actually get: QWERTY where ten columns of about 22 pixels fit, T9 where four of about 28 do, the strip below that. A layout you name is honoured exactly, however cramped, because a stated preference is a decision and not a suggestion.
  2. 02When docking becomes a fiction. If the docked keys would come out under 30 pixels tall, the keyboard stops pretending and takes the whole display, with a mirror of the focused field above it. Because input state is keyed by identifier, the mirror is the field: same text, same caret. A short landscape panel hits this on every layout.
  3. 03The pointer model, in four rules. A stroke that stays within 6 pixels is a tap, and the topmost control wins it. Held still for 500 milliseconds it becomes a long press, and can repeat. Past the slop over a scroll zone it drags, and flings on release. A press within 12 pixels of an edge that travels 40 inward becomes Escape — a back gesture for glass with no corner to put an exit control on.
  4. 04Hardware, from JavaScript. sys.gpio reads, writes and reads an analogue count; sys.i2c moves one byte of a device on the shared bus. A motion module pushes accelerometer, gyroscope and temperature readings into state as patches, on its own schedule and only when a reading has actually moved — so a view of them never polls, it just renders state. The firmware refuses any pin the active board’s display or touch controller uses, from a denylist built out of the same defines that wire them.
  5. 05Zero dependencies, meant literally. Nothing is installed to run the core. The transpiler is 312 lines inside the repository. The single native dependency anywhere in the tree belongs to the optional desktop window, and the window is optional.
  6. 06Limitations, stated rather than hidden. Font metrics are a documented override point and it is easy to forget to copy them, which visibly displaces centred text. Examples authored at fixed pixel sizes do not fit every canvas. Real flexbox was deliberately not built — not for flash or RAM, but because it is a different algorithm with no answer for scrolling and an unverified toolchain risk on the chip’s compiler. The repository says all of this in its own documentation, at length, in about these words.
  1. 1. Colours are 24‑bit values everywhere in the core, and the backend converts to its own depth — 5‑6‑5 on the panels, plain bytes in the headless buffer, a quantised approximation in a terminal that cannot take true colour. The conversion is not lossless on every host, so an application must not compare exact colours across backends. ↩

Colophon & honest notice

mjsx is a hobby project, MIT licensed. It is not published to npm and it is not on GitHub: there is nothing to install and nowhere to star. The package is marked private on purpose. If you end up with a copy, pin it to the repository you got it from.

It was ported out of a working ESP32 firmware’s interface code and generalised until nothing in it assumed a board, an engine, or a particular way of turning a draw call into pixels. It drives four boards daily and it is written by one person for the pleasure of it.
