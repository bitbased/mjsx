01 Subject

Ten drawing calls wide. That is the entire porting contract.

mjsx is JSX for microcontrollers, a Raspberry Pi, the desktop and the browser. One portable core file holds h(), layout, hit‑testing and the touch state machine. It reaches pixels through exactly ten gfx calls plus a clock — and anything that realizes those ten is a backend.

No virtual DOM. No reconciler. No dependencies. The same file runs unmodified inside a chip’s embedded interpreter and in a browser tab, because it is written in the ES5 subset both of them agree on.

02 Principle of operation

State changes, the frame is dirty, the frame redraws.

There is no retained tree to diff and nothing to reconcile. Layout is one pass, width in and height out; drawing is the second. Everything a component needs in order to behave — where it was drawn, what a finger is doing — lives in that same file, so no backend has to reimplement any of it.

ANo reconciler

measure, then draw. A dirty frame is simply drawn again. The engine keeps no shadow tree, so there is no class of bug where the tree and the glass disagree.

BHit‑tested at the drawn rect

A control registers its hit region at the exact rectangle it was painted at. What you touch cannot drift from what you see, because the two come from the same number.

COne touch state machine

Drag slop of 6 px, scroll, fling with per‑zone velocity, long‑press and hold‑repeat. Written once in the core; a backend only feeds it UI.pointer(id, phase, x, y).

DES5 on purpose

The subset MicroQuickJS accepts. The identical file loads as a module under a desktop runtime and is eval’d flat inside a chip, with no branch on the host anywhere in it.

EThe transpiler is in the box

312 lines of JSX→JS, written in the same ES5 subset it emits. It runs in a build script, in a browser, or inside the chip interpreter itself — which is what a device needs in order to accept source rather than a prebuilt bundle.

FColours are plain integers

24‑bit 0xRRGGBB everywhere above the line. The backend converts down to whatever it actually has — 5‑6‑5 on the panels, RGB bytes in the software rasterizer.

03 Native interface

The whole of what a backend must supply.

The core probes for nothing else. Implement this channel map and every example, every component, every keyboard and the entire input model come along unchanged.

On a live target you own the loop instead: tick UI.ticker(), which advances flings, timers and long‑press repeats and reports dirtiness, then UI.render() and present the surface. A new backend is ten functions of a few lines each, a clock, and that loop.

Optional — probed for, never assumed

Three extras are detected with a presence check, and the core has an answer for every one of them being missing.

  • gfx.polyFill polygon rings under a nonzero or even‑odd rule, so a backend can rasterize paths at device resolution. Without it the core scanline‑fills through frect on its own.
  • gfx.blitComposite external pixels for the canvas element — a camera frame, a bitmap. A backend without it draws a crossed placeholder instead.
  • sys.store
    sys.fetch    A persistent string store. On a board that is NVS, so an app’s settings survive a power cycle; elsewhere the core falls back on its own.

Font metrics are the documented override point rather than a hidden special case: the core defaults to a fixed bitmap metric, and a backend whose pixels are not really pixels — a terminal, where one unit is one character cell — replaces FONT after loading the core.

04 Specimen

A whole stateful application.

Tap the button; the count changes; the screen is redrawn to match. That is the entire mechanism — state, UI.set, full redraw. Every example in the repository is one flat app.jsx written against the ambient globals a host provides, with no imports and no build step, and each of them runs unmodified under every backend.

Verbatim examples/counter/app.jsx 
function App() {  var count = UI.state.count || 0;  return (    <box pad={em(2)} gap={em(2)}>      <text text={'COUNT: ' + count} size={3} color={UI.theme.text} align="center" />      <Button label="+1" size={2}              onTap={function () { UI.set({ count: count + 1 }); }} />    </box>  );} UI.mount(App);

›em(), not pixels

Spacing is expressed in the host font’s own metric, so one source keeps its proportions on a 172‑pixel strip and on a 320×480 panel.

›Ambient globals

h, UI, gfx and sys come from the host. An example imports nothing, which is exactly what lets it be pushed to a chip as plain text.

›Self‑checking

The same file exports a demo hook that drives a genuine simulated touch through UI.pointer — press and release at the control’s registered rect — instead of calling the handler directly, so the hit test is under test too.

05 Targets

Six backends. Nothing above the line changes.

Each one implements the same ten functions, and nothing is special‑cased per target. gfx.frect writes into an RGBA buffer, or into a sub‑pixel buffer flushed as terminal escapes, or is a C function writing a real panel.

  • PURE‑JS

    Headless software rasterizer into an RGBA buffer, writing a real PNG. The reference implementation, and the renderer two of the other backends draw with.

  • TERMINAL

    Near‑square pixels in a terminal — two sub‑pixels per character cell via the half‑block glyph, colour as ANSI. One runner renders a single frame; another is a real raw‑mode interactive app.

  • SDL

    A device simulator in a native window: square, rounded‑corner and round masks, size presets for the actual panels, an HD sub‑pixel mode and host‑font text.

  • HTTP

    The device screen mirrored into a browser tab over a WebSocket — pixels out, real input back, including genuine per‑finger multitouch.

  • WASM

    The same MicroQuickJS engine source compiled with Emscripten, running the same bytecode a chip runs. Engine parity for testing, not a reimplementation of it.

  • ESP32

    The real thing. A minimal reference firmware shows exactly where a panel driver plugs in; the bridge firmware takes core, shim and examples bundled as plain JS over TCP — no reflash.

06 Round glass

A circle has no rows.

At every height, the width a layout actually has is the chord of the circle, not the bounding box — and it narrows fastest exactly where a keyboard’s bottom row wants to sit. mjsx measures the chord across each band and insets that row to fit it, so the keyboard comes out as a trapezoid instead of pushing SPACE and OK under the bezel.

The OK key parks in the bottom arc — the sliver below the grid that a full‑width row could never have used anyway — so it costs the keyboard no height at all. And ArcFooter puts controls along the rim: each item lands where the ray from screen centre meets the boundary, pulled inward by its own size, staying upright, because rotated text is neither drawable nor readable. On square glass the same call walks the rectangle’s perimeter instead, so a bottom arc simply becomes the bottom edge.

Text entry chooses itself

auto measures the width the keys really get — on round glass the chord down where the bottom rows land, not the 240 across the middle — and picks from there.

  • ≥ 220 pxQWERTY — ten columns want about 22 px each, with a shift key and a symbols page.
  • ≥ 115 pxT9 — four columns at roughly 28 px, cycling keys, and a themed symbol table so the whole repertoire stays reachable.
  • < 115 pxSTRIP — one scrolling row of characters you drag through. Under T9’s width it is the only honestly tappable option left.
  • BY NAMENUMBERS — the fourth layout, asked for outright when a field wants digits.

One more guard: if the docked keys come out shorter than a finger, the keyboard takes the whole display rather than pretending to dock. A short landscape panel hits that on every layout, and nobody should have to opt in to legible keys.

“A named layout is honoured exactly, however cramped — a stated preference is a decision, not a suggestion.” packages/core/src/mjsx.js

07 Hardware access

Pins and buses, from JavaScript.

The bridge firmware exposes the board itself to an app, so a panel of controls and the thing it controls end up being the same program.

GPIOsys.gpio(pin, op, value)

Read with the pull‑up applied, drive a level, or take an ADC count. Pins the active board’s display or touch controller own are refused and answer -1 — and the example shows that refusal rather than hiding it.

I2Csys.i2c

Scan the bus across the usual address range and peek at a device’s registers: the firmware’s own diagnostic command, given a face.

IMUMotion module

Accelerometer, gyroscope and temperature, plus a magnetometer when one is wired. It pushes state patches on its own schedule and only when a reading has actually moved, so a view never polls — it renders state, and is redrawn when that state changes.

Every one of these examples ships a no‑hardware stand‑in, so the whole flow stays clickable on a desktop and says plainly which of the two you are looking at. It is also why the example gallery renders deterministically: the fallbacks read no clock, so the images do not move between runs.

08 Status

A hobby project, open‑sourced as‑is.

mjsx was lifted out of a working ESP32 firmware’s UI engine and generalized until nothing in it assumed a particular board, a particular interpreter, or a particular way of turning a draw call into pixels. It is not a product, and it has no roadmap you could hold it to.

It is not published to npm — the package is marked private on purpose — and it is not on GitHub. Pin to the repository if you want to use it. MIT licensed. The known limitations are written down in the docs beside the features, including the ones that are still concessions.
